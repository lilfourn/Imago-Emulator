### Screen turned off (5 games)

No error, but every screen is one colour at each checked frame. At the frame budget the LCD is off (LCDC bit 7 clear), and pressing buttons doesn't help. PC is where the CPU ran in the last second. Op is the two bytes at the PC: 76 is HALT (the PC shows the byte after it), 10 STOP, 18FE a jump to itself, FF RST 38 (code running through empty ROM), F041 a read of STAT. KEY1 FE means the game switched to double speed. A HALT waiting on VBlank or LCD STAT (IE bits 0 and 1) never wakes while the LCD is off, on hardware too, so the fault comes before. Lead: set a debugger watchpoint on 0xFF40 to see where the LCD goes off, and trace back from there; compare with SameBoy or mGBA on the same ROM. 4 of them loop on `ldh a,(STAT); and 2; jr z`, waiting for mode 2 or 3, which an LCD that is off never reports; 3 of those switched to double speed first (KEY1 FE). The loop would hang on hardware too, so look at what turned the LCD off: the LCDC writes, and LY and STAT timing around and after the speed switch.

### GBA header without the fixed byte 0x96 (1 game)

- `not a valid gba rom: header fixed value at 0xB2 is not 0x96` (1): [crates/emu-gba/src/lib.rs:98](../../crates/emu-gba/src/lib.rs#L98)

Every byte of the header from 0x04 to 0xBF is zero: no Nintendo logo, no fixed byte, no complement check. GBATEK marks the logo, the 0x96 at 0xB2 and the complement at 0xBD as required, and says the BIOS locks up when the logo differs; it does not say whether the BIOS reads 0xB2 itself (the complement covers it). The core starts games without a BIOS, so the check only serves to recognise a GBA ROM. Lead: drop it, or recognise a ROM by the ARM branch at 0x0 (byte 3 is 0xEA). With 0xB2 patched to 0x96: hh:dangerous-xmas ok (frame 900).

## Systems without a core

The PRD lists 3DS cores as a non-goal (section 4): Gen 6-9 support, if it ever comes, means hosting an existing core, never writing one. Phase 5 of the roadmap is a libretro-host mode for an existing core (for example one derived from Azahar), or contributing to Azahar, with parts of a 3DS emulator (an ARM11 interpreter, a PICA200 shader interpreter) written only for learning, against homebrew. 3DS homebrew (`.3dsx`, and `.cia` builds of it) is not encrypted, so it needs no keys, which the legal policy rules out (PRD section 9).
